# Backend Career Quest

Реализованы три маршрута из задания Дамира: завершение активности, импорт профилей/истории
и HR-сводка. URL и Pydantic-контракт `shared/contracts.py` сохранены.

## Запуск и состояние

Из корня проекта после установки зависимостей и подготовки исходных файлов:

```powershell
.\.venv\Scripts\python.exe run.py --dev
```

Сервер использует один worker. При первом запуске создаётся `.local/career_quest.sqlite3`:
актуальный snapshot, исходная история, отдельный журнал runtime-завершений и результаты
идемпотентных операций. Каталоги и импортированные профили сохраняются в snapshot.
При следующем запуске состояние восстанавливается из SQLite. Исходные JSON/CSV не изменяются.
Можно задать серверную переменную `STATE_PATH`, как в `.env.example`; относительный путь считается от корня проекта.
Для независимого демонстрационного прогона укажите новый путь внутри `.local/`.

## Поведение API

- Completion проверяет права, версию, аудиторию, prerequisites и реальное участие/сессию.
  Будущую сессию завершить нельзя. При единственном `in_progress` обычной активности
  сервер связывает завершение с ним автоматически; при нескольких нужно указать record ID.
- Повтор исходного запроса возвращает сохранённые числа и версию с `already_applied=true`,
  даже если текущая версия уже изменилась. Изменённый запрос с тем же ключом получает 409.
  Новый ключ для завершённой обычной активности не даёт прироста и не увеличивает версию.
- Для `EV_036` обязательны `participation_record_id` или `session_date`.
  Два запроса на одну сессию не начисляют навыки дважды. Новая сессия должна быть
  известна каталогу и уже наступить либо соответствовать начатому участию из истории.
- `completed_at` использует модельную дату `as_of_date`, не календарь компьютера.
  Время после полудня с последовательными микросекундами — логический порядок операций
  внутри модельного дня, не измеренное реальное время обучения.
  Завершение в день последней оценки считается новой операцией после этой оценки.
- Импорт принимает `employees` и/или `history`, до 5 MiB на файл, включая UTF-8 BOM.
  Все ссылки проверяются на объединённом snapshot. Профили заменяются по employee ID,
  история объединяется по record ID; конфликт отклоняет весь импорт. Повторяющиеся record ID
  внутри одного CSV отклоняются с 422, даже если строки полностью одинаковы. Идентичный импорт
  не изменяет версию. Импорт не может повторно внести live-завершение как новую completed-запись.
- HR агрегирует навыки и участие локально. Завершённое начатое участие остаётся одной
  записью со статусом `completed`. Знаменатель gap rate — сотрудники, которым нужен навык.
- Кэш рекомендаций ограничен 512 ответами и зависит от employee ID, версии и серверной
  AI/LLM-конфигурации. Изменения данных очищают кэш; опоздавший ответ прежней версии
  не возвращается в кэш. Его HTTP-ответ сохраняет исходный `data_version`.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe scripts/check_dataset.py
.\.venv\Scripts\python.exe scripts/check_backend.py
```

Проверено 23 сентября 2026: 76 тестов прошли. Единственное предупреждение — deprecation
в связке Starlette/AnyIO, оно не связано с прикладным кодом.
Проверка исходных данных: 200 сотрудников, 40 событий, 60 навыков, 2743 строки истории.
`check_backend.py` использует временную SQLite, делает completion/retry, импортирует
три regression-профиля из `docs/jury_examples`, проверяет рекомендации, HR и восстановление
после пересоздания приложения. Контрольные суммы исходных файлов остаются прежними.
Пример проверенного прироста покрытия: 71.93 → 73.68%.

Тесты также проверяют одновременные retry, откат при ошибке SQLite, конфликты ключа/версии,
повторяемые сессии, авторизацию, невалидные ссылки/форматы/размеры и инвалидирование кэша.
Добавлены проверки дубликатов record ID (одинаковые/различающиеся строки, новые/сохранённые ID)
с откатом всего импорта и восстановления состояния через STATE_PATH (default/relative/absolute).

## Границы готовности

Это проверка backend через FastAPI TestClient и повторное открытие SQLite. Сквозная
проверка в браузере и реальный вызов разрешённого LLM остаются общей интеграционной задачей.
`check_backend.py` намеренно использует явный `fallback` и не отправляет данные провайдеру.
Работа нескольких backend workers не поддерживается. Общие README/START_HERE/API_CONTRACT
пока содержат первоначальный статус starter; текущий отчёт backend находится здесь.
